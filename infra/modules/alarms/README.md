# `alarms`

Owns the CloudWatch metric alarms that watch the finished stack: one `Errors` alarm per Lambda function, a dedicated `Throttles` alarm on the ingest function, and two RDS alarms on free storage and CPU. Every alarm publishes both `ALARM` and `OK` transitions to the SNS topic created by `observability`. It creates no metrics, no topic and no keys — only alarms, and it is applied last.

## Design notes

**The reason this is not part of `observability` is a dependency cycle, and the header comment spells it out.** An alarm needs the *identifiers* of things created late — Lambda function names, the RDS instance id. Those same resources encrypt with CMKs created early, in `observability`. Put the keys and the alarms in one module and that module would depend on the resources that depend on it, which Terraform rejects. So the split is along the direction of dependency rather than along subject matter: `observability` produces (keys, trail, secret, topic) and is applied first; `alarms` consumes (names and ids) and is applied last. The variables file opens with a one-line reminder of this, which is worth keeping — it is the kind of thing that gets "tidied up" into a cycle by someone six months later.

**Lambda error alarms are generated by `for_each` over the whole function map.** Adding a function to `modules/lambda` gives it an error alarm automatically, with no second edit. That is the same structural-by-construction approach the lambda module takes with roles.

**The RDS free-storage threshold is computed from a percentage, not hard-coded in bytes.** `FreeStorageSpace` is reported in bytes, and a fixed byte threshold silently becomes meaningless the moment someone resizes the instance — 4 GB free is an emergency on a 20 GB volume and unremarkable on 200 GB. The local multiplies `rds_allocated_storage_gb` by the percentage, and the computed value is exported as `rds_free_storage_threshold_bytes` so a runbook can quote the exact number the alarm uses rather than an approximation.

**`treat_missing_data` differs per alarm, deliberately.** Free storage uses `breaching`: if the instance stops publishing `FreeStorageSpace`, something is wrong with the database and silence is not reassurance. Everything else uses `notBreaching`, because a Lambda that was not invoked publishes no `Errors` datapoint at all, and treating that as a breach would leave every low-traffic function permanently in alarm.

**The ingest throttle alarm has its own resource and its own words.** Throttles on `ingest-events` are not a generic error — they are the reserved-concurrency valve doing its job, which means agents are receiving 429s and backing off. The alarm description says exactly that, so whoever gets the page knows they are looking at a capacity signal rather than a fault. Two evaluation periods rather than one, so a single transient spike does not page anyone.

**Both `alarm_actions` and `ok_actions` are wired on every alarm.** Recovery is notified, not just failure. Without `ok_actions` an operator has to go and check whether the thing that paged them at 2 am has resolved.

**Five minutes and two periods, uniformly.** Every alarm uses a 300-second period; the Lambda error alarms evaluate one period and the rest evaluate two. Nothing here tries to be a sub-minute detection system, which is consistent with a batch-ingest workload sampling at 60-second intervals.

## Inputs

| Name | Type | Default | Description |
|---|---|---|---|
| `name_prefix` | `string` | required | Prefix applied to every alarm name, e.g. `worklens-prod`. |
| `tags` | `map(string)` | `{}` | Tags applied to every alarm. |
| `alarm_topic_arn` | `string` | required | SNS topic that receives alarm and OK notifications, from `modules/observability`. |
| `lambda_function_names` | `map(string)` | `{}` | Map of logical function key => Lambda function name, used to build per-function error alarms. |
| `lambda_error_threshold` | `number` | `5` | Number of Lambda errors in a 5 minute period that trips the per-function alarm. |
| `ingest_function_name` | `string` | required | Function name of the ingest handler, alarmed separately for throttles. |
| `rds_instance_id` | `string` | required | RDS DB instance identifier to alarm on. |
| `rds_allocated_storage_gb` | `number` | required | Allocated storage of the RDS instance in GiB; the free-storage alarm threshold is derived from it. |
| `rds_free_storage_threshold_pct` | `number` | `20` | Percentage of allocated storage below which the RDS free-storage alarm trips. |
| `rds_cpu_threshold_pct` | `number` | `80` | Average CPU utilisation (%) over 10 minutes that trips the RDS CPU alarm. |

## Outputs

| Name | Description |
|---|---|
| `lambda_error_alarm_names` | Map of logical function key to the name of its error alarm. |
| `alarm_names` | Every alarm this module created, for the deploy summary and for runbook cross-references. |
| `rds_free_storage_threshold_bytes` | The computed `FreeStorageSpace` threshold, so the runbook can quote the same number the alarm uses. |

## Security notes

This module implements no row of `docs/PLAN.md` §6 directly — it creates no data path, holds no credential and grants no permission. Its contribution is detection rather than prevention: §6's closing paragraph relies on reserved concurrency protecting the database, and the ingest throttle alarm is what makes that control observable instead of silent. The per-function error alarms are, in practice, how you find out that the retention sweeper has stopped running, which matters for row 11.

The one thing worth noting is what is *not* alarmed here: there is no alarm on API Gateway 5xx rates, on WAF block volume, or on CloudTrail delivery failure. Those are real detection gaps rather than deliberate omissions with a recorded reason. The scheduled-job dead-letter alarm lives in `modules/scheduling` alongside the queue it watches.

## Gotchas / operational notes

- **`rds_allocated_storage_gb` is fed from a variable, not from the database module.** The root stack passes `var.db_allocated_storage`, while the `database` module has storage autoscaling enabled up to `max_allocated_storage` (default 100 GiB against an initial 20). Once autoscaling has grown the volume, the alarm threshold still reflects the original allocation — so a "20% free" alarm becomes a 4% alarm on a 100 GiB volume, and you lose most of your warning. After any storage growth, update `db_allocated_storage` to match reality or the alarm is worse than useless.
- **One error threshold applies to every function, and they are not comparable.** Five errors in five minutes is background noise on `ingest-events` and a serious incident on `pre-token-generation` — where five errors means five people could not log in — or on `db-migrate`, where any error at all matters. The single `lambda_error_threshold` is a compromise; if you need per-function thresholds, this is where to add them.
- **`treat_missing_data = "breaching"` on free storage alarms on a stopped instance.** Stopping the RDS instance, or a long failover, stops the metric and trips the alarm. That is the intended behaviour, but expect noise during planned maintenance.
- **`lambda_function_names` defaults to an empty map,** so a caller who forgets to pass it gets a module that applies cleanly and creates no Lambda alarms at all. Nothing warns.
- **Alarm names embed `name_prefix` and the function key.** Renaming either replaces the alarm, which breaks any runbook or dashboard referencing the old name — use the `alarm_names` output as the source of truth rather than hard-coding names elsewhere.
- **`alarm_topic_arn` is required and not nullable here** (unlike `modules/scheduling`, where a `null` disables its alarm). There is no way to create these alarms without a topic.
- **Alarms are billed per alarm per month.** The Lambda error alarms scale one-for-one with the function catalogue, so adding functions has a small but real recurring cost.
- **The ingest function gets two alarms.** It appears in `lambda_function_names` (error alarm) *and* as `ingest_function_name` (throttle alarm). That is intentional, but be aware a capacity incident can produce two notifications for one cause.
- **Every alarm evaluates against a 300-second period.** Nothing here will catch a fault that resolves in under five minutes, and the RDS alarms need two periods, so worst-case detection latency is around ten minutes.
